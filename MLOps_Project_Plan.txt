  MLOps PROJECT PLAN
  Energy Price Forecasting — Pipeline Engineering + ML Research Programme

OVERVIEW
--------
This document covers two interleaved things:

  1. PIPELINE ENGINEERING — building a production-grade MLOps skeleton that
     demonstrates infrastructure competency (MLflow, Docker, FastAPI, CI/CD,
     drift detection, Airflow). This is the MLOps portfolio piece.

  2. ML RESEARCH PROGRAMME — using that pipeline as a tool to systematically
     study what drives forecast quality: feature selection/ablation, derivative
     features, temporal resolution, prediction horizon, and model architecture.
     This is the data science portfolio piece.

They share the same codebase. Build the pipeline first; run the research
programme through it. The pipeline becomes the instrument; the research
programme generates the results that make the project scientifically
interesting.

Data source: ENTSO-E Transparency Platform (https://transparency.entsoe.eu)
  - Day-ahead electricity prices for Poland (PSE bidding zone)
  - Actual load, generation by source (wind, solar, gas, coal, etc.)
  - Cross-border flows
  - All downloadable as CSV, free registration required
  - Hourly resolution going back to ~2015

Secondary data sources to add during the research phase:
  - Polish public holidays: publicly available JSON/CSV from multiple sources
  - Weather data: Open-Meteo API (free, no key required for historical data)
    Relevant variables: temperature, wind speed, solar irradiance, cloud cover
    for the main Polish load centres (Warsaw, Kraków, Gdańsk, Wrocław)
  - ERA5 reanalysis (via Copernicus CDS) for higher-quality historical weather

    enabled: true

================================================================================
  THE SWAPPABLE ARCHITECTURE — IMPLEMENTATION NOTES
================================================================================

WHAT IS WORTH MAKING SWAPPABLE (via params.yaml):
  - Model class and all hyperparameters
  - Which feature groups are active (boolean flags)
  - Temporal resolution and prediction horizon
  - Train/val/test split boundaries
  - Which metrics to compute
  - Which categorical variables to use in residual breakdown

HOW TO IMPLEMENT MODEL SWAPPING:
  Dynamic import pattern in train.py:

    import importlib, yaml

    def load_model(cfg):
        # cfg["model"]["type"] = "xgboost.XGBRegressor"
        module_path, class_name = cfg["model"]["type"].rsplit(".", 1)
        module = importlib.import_module(module_path)
        return getattr(module, class_name)(**cfg["model"]["params"])

  This means switching from XGBoost to LightGBM to sklearn Ridge is:
    model:
      type: lightgbm.LGBMRegressor
  No code change required.

  For PyTorch models (later phase): define a thin wrapper class that exposes
  .fit(X, y) and .predict(X) so the training loop doesn't need to know whether
  it's talking to sklearn or PyTorch. One wrapper per architecture.

WHAT IS NOT WORTH MAKING SWAPPABLE:
  - Feature engineering logic in featurise.py
    Each feature group is a self-contained function; the config flags decide
    which functions are called. But the functions themselves are domain-specific
    and should not be abstracted into a generic transformer.

  - FastAPI endpoint structure
    The serve.py is thin: it loads a model from the MLflow registry and calls
    .predict(). That's the interface. Don't over-engineer it.

  - Docker topology
    The same docker-compose.yml works for all experiments. It just runs
    different params.yaml files.

MAKEFILE TARGETS (the single-command workflow):
  make ingest     → run ingest.py (download + validate raw data)
  make featurise  → run featurise.py with current params.yaml
  make train      → run train.py (logs to MLflow, saves to registry)
  make serve      → start FastAPI + MLflow via docker-compose
  make report     → run monitor.py (generate Evidently drift + residual report)
  make all        → ingest → featurise → train → serve → report
  make test       → run pytest

PHILOSOPHY:

  Structure each entry in EXPERIMENTS.md as:

    Hypothesis: calendar features alone capture most of the weekly seasonality.
    Config diff: all feature flags false except calendar.enabled: true
    Result: RMSE=..., MAE=..., R²=...
    Finding: ...

------------------------------------------------------------------------
  EXPERIMENT SERIES A: FEATURE ABLATION
  Question: which feature groups add value, and how much?
------------------------------------------------------------------------

  [ ] EXP-001: Calendar features only (baseline, already done in Stage 2)

  [ ] EXP-002: Calendar + weather
        params diff: features.weather.enabled: true
        Hypothesis: weather explains solar/wind generation and therefore price
        Expected: improvement, especially in hours with high renewable penetration

  [ ] EXP-003: Calendar + lags only
        params diff: features.weather.enabled: false, lags.enabled: true
        Expected: strong improvement — price has strong autocorrelation

  [ ] EXP-004: Calendar + lags + weather
        All three enabled. Expected: best so far.

  [ ] EXP-005: Add generation mix
        Hypothesis: knowing actual wind/solar generation improves forecast
        Caveat: in real deployment you'd need generation forecasts, not actuals.
        Note this in EXPERIMENTS.md — it's a data leakage risk in deployment.

  [ ] EXP-006: Add cross-border flows
        Polish prices are coupled to DE/CZ/SK markets via interconnectors.
        Hypothesis: import/export flows add signal about price pressure.

  [ ] EXP-007: Holiday-adjacent features
        days_to_next_holiday, days_since_last_holiday, is_long_weekend
        Hypothesis: prices behave differently in the 1–2 days before a holiday.
        Look for this in residual analysis from EXP-004 before running.

------------------------------------------------------------------------
  EXPERIMENT SERIES B: DERIVATIVE FEATURES
  Question: do explicit first and second derivatives of price improve forecasts?
------------------------------------------------------------------------

  IMPLEMENTATION NOTE:
    Raw price derivatives amplify noise. Before computing:
      1. Apply a short rolling mean (window=3h) to smooth
      2. Then compute diff(1) for first derivative, diff(2) for second
    Log the smoothing window as a hyperparameter.

    Conceptually: first derivative = price velocity (is price rising or falling?)
    Second derivative = price acceleration (is the rise/fall speeding up?)
    These capture momentum that lag features partially miss.

  [ ] EXP-008: Add first derivative of price (smoothed)
        params diff: features.derivatives.enabled: true, order: [1]
        Compare to EXP-004 (same other features)

  [ ] EXP-009: Add first + second derivative
        params diff: features.derivatives.order: [1, 2]
        Watch for: if second derivative hurts, noise is dominating.

  [ ] EXP-010: Vary smoothing window (3, 6, 12 hours)
        If derivatives help, find the right smoothing level.
        Log smooth_window as an MLflow parameter.

  [ ] EXP-011: Derivatives of weather variables
        Same logic: rate of change of temperature or wind speed may be
        more predictive than the level. Try wind_speed first derivative.

  RESIDUAL ANALYSIS for Series B:
    After each run, plot residuals vs price-change-direction (rising/falling).
    If derivatives help, residuals should be more symmetric around zero in
    periods of rapid price movement.

------------------------------------------------------------------------
  EXPERIMENT SERIES C: TEMPORAL RESOLUTION
  Question: does the right time tick depend on the prediction task?
------------------------------------------------------------------------

  IMPLEMENTATION NOTE:
    Resampling is handled in featurise.py, gated by params.temporal.resolution.
    When resampling to daily: use mean price for the day as target (or VWAP).
    When resampling to weekly: use mean price for the week.
    Lag periods need to rescale accordingly (params.lags.periods in native units).

  [ ] EXP-012: Daily resolution, 7-day horizon
        Resample hourly data to daily. Predict next 7 days.
        Features: day-of-week, week-of-year, is_holiday, 7-day lags.

  [ ] EXP-013: Weekly resolution, 4-week horizon
        Resample to weekly. Predict next 4 weeks.
        Features: week-of-year, month, lagged weekly means.

  [ ] EXP-014: Hourly, 48-hour horizon (extend from 24h)
        Does accuracy degrade with horizon? At what rate?
        Implement as multi-step: train 24 separate models (one per horizon step)
        OR use a single model with horizon step as a feature.
        Note: single model is simpler to deploy; separate models usually win.

  [ ] EXP-015: Hourly, 168-hour horizon (1 week ahead at hourly resolution)
        At what horizon does the hourly model become worse than the daily model?
        This is a scientifically interesting crossover point.

------------------------------------------------------------------------
  EXPERIMENT SERIES D: MODEL ARCHITECTURE COMPARISON
  Question: for this problem and dataset, which model class is best?
------------------------------------------------------------------------

  [ ] EXP-016: LightGBM (same hyperparameters as XGBoost baseline)
        params diff: model.type: "lightgbm.LGBMRegressor"
        Usually faster than XGBoost; sometimes better on tabular data.

  [ ] EXP-017: Ridge regression (linear baseline)
        params diff: model.type: "sklearn.linear_model.Ridge"
        If linear model is within 10% of XGBoost, the features are doing
        the work, not the model. Important diagnostic.

  [ ] EXP-018: Random Forest
        params diff: model.type: "sklearn.ensemble.RandomForestRegressor"
        Useful comparison for understanding XGBoost's advantage.

  [ ] EXP-019: CatBoost (handles categorical features natively)
        Interesting for is_holiday, day_of_week without encoding.
        params diff: model.type: "catboost.CatBoostRegressor"

  [ ] EXP-020: LSTM (first neural network experiment)
        Requires PyTorch wrapper implementing .fit()/.predict() interface.
        Build the wrapper as a separate class; the training loop is
        the main new code. Log loss curve as MLflow artifact.
        Key hyperparameters to expose: hidden_size, num_layers, dropout,
        sequence_length, batch_size, learning_rate.
        Only run this after tabular models are well-tuned —
        LSTMs rarely beat gradient boosting on tabular time-series
        without careful feature engineering and longer training.

  [ ] EXP-021: Temporal Fusion Transformer (TFT)
        State-of-the-art for multi-horizon time-series forecasting.
        Use pytorch-forecasting library (wraps PyTorch Lightning).
        Highest complexity; run last, after understanding the data well.

  NOTES FOR LATER — NEURAL NETWORK PHASE

  Do not start here. Only move to neural networks after:
    (a) You have clean tabular results from Series A–D
    (b) You understand which features matter and why
    (c) You have a well-tuned XGBoost/LightGBM baseline to beat

  The most likely useful architectures for this problem, in order of complexity:
    1. LSTM: straightforward to implement with PyTorch; understands sequences
             natively. Likely competitive with XGBoost if features are sparse.
    2. Temporal Fusion Transformer (TFT): state of the art for multi-horizon
             tabular time-series. pytorch-forecasting library wraps it.
             Interpretable: produces attention weights showing which lags matter.
    3. N-BEATS / N-HiTS: pure time-series decomposition networks.
             No feature engineering needed — they learn seasonality internally.
             Interesting comparison: do hand-crafted features beat the network's
             learned decomposition?

  Neural network hyperparameter search:
    Use Optuna for hyperparameter optimisation (integrates with MLflow).
    Define the search space in params.yaml; Optuna samples it.
    Log each trial as a separate MLflow run.
    This adds one more portfolio-worthy tool to the stack.
